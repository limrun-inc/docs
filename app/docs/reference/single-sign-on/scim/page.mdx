# SCIM provisioning

SCIM manages organization membership. [OIDC SSO](/docs/reference/single-sign-on) handles sign-in. Configure SSO and verify your email domains before connecting provisioning.

## Connect your directory

1. Open **Settings > Single Sign-On > Directory provisioning (SCIM)** as an organization admin.
2. Generate a credential. Copy the **SCIM base URL** and bearer credential into your provider's SCIM 2.0 configuration. The credential is shown once and grants provisioning access to this organization only.
3. Enable user creation, profile updates, and deactivation. Disable group provisioning and Group Push. Set SCIM `userName` to the same work email sent in the OIDC `email` claim, within a verified organization domain.
4. Assign users in your provider and refresh the directory in Limrun. Groups may determine assignments inside the provider, but Limrun does not synchronize groups or map them to roles.
5. Choose who manages roles using **Manage roles through the identity provider**, then select **Save role policy**. See the role modes below.
6. Check the provisioned users and their eligible roles, including an administrator who should retain access. Select **Activate SCIM**.

During setup, users synchronize while existing members retain access. Newly provisioned users cannot sign in until activation. Activation is permanent. Directory changes apply immediately once active. Policy revisions prevent an administrator from overwriting a concurrent policy change; refresh if prompted.

## Choose who manages roles

### Administrators in Limrun

Leave **Manage roles through the identity provider** disabled. Administrators can change existing members' roles in **Settings > Members**. SCIM profile updates preserve those roles and reject requests that assign roles.

Newly provisioned active users receive the organization's **Default role for new members** when SCIM is active. Deactivation removes membership. Reactivation assigns the current default role, which may differ from the user's previous role. Existing members retain their role during activation if they are active in the provisioned directory.

### Identity provider

Enable **Manage roles through the identity provider** and select **Save role policy** before synchronizing role assignments. Console role edits are blocked. Configure the provider to send exactly one of `admin`, `member`, or `viewer` through the SCIM User `roles` attribute:

```json
{"roles": [{"value": "member"}]}
```

The provider can derive this assignment from its own groups or policies. Limrun receives the resulting role, not the groups. An active user without an assigned role has no access. Removing the role removes membership. Deactivation retains the assignment for reactivation; deleting the SCIM user removes it. A replacement `PUT` that omits `roles` clears the assignment; a profile-only `PATCH` preserves it.

Enabling provider-managed roles copies current memberships into initial assignments for their SCIM identities. Review those assignments in your provider. Before activation, assignments synchronize without granting access.

Disabling provider-managed roles clears provider assignments and preserves existing membership roles. When SCIM is active, active provisioned users who had no role receive the default role. Re-enabling seeds from current memberships, so old provider assignments do not return.

## Identity provider setup

SSO and provisioning require separate configuration. Installing an SSO application does not start synchronization. Use the generated SCIM bearer credential, not a Limrun API key or the SSO application's client secret.

- **Okta:** Configure SCIM 2.0 with bearer authentication. Enable user provisioning and leave Group Push disabled. See [Okta SSO](/docs/reference/single-sign-on/okta) for authentication setup.
- **Microsoft Entra ID:** Configure automatic user provisioning in a non-gallery enterprise application. Use the SCIM base URL and credential as the Secret Token, and disable group provisioning. See the [Entra guide](/docs/reference/single-sign-on/microsoft-entra#configure-scim-provisioning).

### Okta entitlement configuration

Okta Identity Governance is required for entitlement management. Enable schema discovery and configure the Role entitlement as follows:

| Setting | Value |
|---|---|
| Resource Type | `Role` |
| Endpoint | `/Roles` |
| Multi-valued | Disabled |
| ID attribute | `id` |
| Display Name attribute | `displayName` |
| Description attribute | Leave blank |

Okta discovers Admin, Member, and Viewer. Assign roles individually or through entitlement policies, and enable provider-managed roles in Limrun before synchronizing them. See [Okta's entitlement management guide](https://developer.okta.com/docs/guides/scim-with-entitlements/main/).

## Access and recovery

Activation removes membership for users who are absent from the provisioned directory or inactive. Provider-managed roles also require a role assignment. SCIM can remove or demote the last admin. In provider-managed mode, restore administration by assigning `admin` to an active user in the provider. In console-managed mode, if no administrator remains, contact Limrun support; new or reactivated users receive the default Member or Viewer role.

Connecting SCIM disables domain auto-join, invitations, and manual membership additions and removals, including during setup. Role edits follow the selected ownership mode. Having an email in the organization's domain is not enough to join. SSO remains required for verified domains.

Deactivation or deletion removes this organization's user access and revokes user-approved MCP grants. Role downgrades also revoke those grants. Other organizations, shared organization API keys, and already-running instances are preserved.

After activation, test sign-in, role changes, deactivation, and reactivation with a pilot user. Check provider logs and Limrun's provisioning history. Access changes take effect when Limrun receives the request, subject to the provider's synchronization schedule.

## Manage the connection

The provisioning screen shows users, their eligible roles, and provisioning history. **Rotate credential** immediately invalidates the old credential. **Revoke credential** stops provisioning without changing membership or role ownership. Neither action disables SCIM enforcement. The configured SSO connection and verified domains cannot be removed while SCIM is configured.

## Protocol support

The base URL serves `/Users`, read-only `/Roles`, `/ServiceProviderConfig`, `/ResourceTypes`, and `/Schemas`. `/Groups` is not supported. Users support create, read, replace, atomic PATCH, and delete. Lists support `startIndex` and `count`, with up to 1,000 results per request. A zero count returns only the total.

User lists support equality filters on `userName`, `externalId`, and `id`. User names match without regard to case. Role lists support equality filters on `id` and `displayName`. Unsupported filters return `invalidFilter`. Use either `attributes` or `excludedAttributes` to project responses, including sub-attributes such as `name.givenName`.

Requests are limited to 1 MiB. PATCH supports up to 100 operations and applies atomically. Value filters support compound expressions such as `emails[type eq "work" and primary eq true].value`. Filter evaluation and output limits return HTTP 413 when exceeded. Send `active` as a JSON boolean. Server-assigned attributes such as `id` are ignored in create and replace requests.

Bulk requests, sorting, password provisioning, enterprise extensions, and ETags are not supported. Discovery endpoints advertise the supported core profile attributes and capabilities.
