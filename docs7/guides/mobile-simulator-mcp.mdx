A coding agent that writes mobile code cannot tell whether the code works until it can open the app and look. Limrun's MCP servers give the agent a cloud iOS simulator or Android emulator it can launch, tap through, read back, and hand to you as a link.

This guide is the task view: launching a device, driving a flow, reading what happened, and fixing a session that misbehaves. Connect your agent first:

- [Remote MCP server](/agents/remote-mcp): one endpoint for your organization. The agent creates and deletes its own devices.
- [Per-instance MCP server](/agents/mcp): one endpoint per simulator, authenticated with that instance's token. Use it when the agent should hold credentials for one device and nothing else.

Both pages list every tool and its arguments.

## Launch a simulator

Through the remote server, the agent calls `create-ios-simulator`. The call blocks until the simulator is ready and returns its instance ID, which every device tool takes as `instanceId`. Three optional fields are worth setting:

- `apps` installs apps at boot, by asset name or by public URL of a simulator build.
- `inactivityTimeout` terminates the simulator after a period without interaction, such as `"10m"`.
- `idempotencyKey` makes a retried call return the same simulator instead of creating a second one.

Instances created this way carry the label `created-by: mcp`, so you can find them later.

With the per-instance server, you create the simulator yourself and hand its MCP URL and token to the agent. From the CLI:

```bash
lim ios create --reuse-if-exists --label agent=session-14 --inactivity-timeout 10m
```

Labels scope reuse and cleanup to one agent, pull request, or session. `--reuse-if-exists` needs at least one label and returns an instance whose labels match exactly. List the instances for a session later with `lim ios list --label-selector "agent=session-14"`.

## Drive a flow

The loop is the same every time: read the screen, act, read the screen again. `ios-screenshot-and-element-tree` returns the screenshot and the accessibility element tree in one call, and the tree is the source of truth: each element's label, accessibility ID, type, and frame.

`ios-use` runs a batch of actions in order. This batch taps an email field, types into it, presses Enter, and taps a button, all in one round trip:

```json
{
  "instanceId": "ios_...",
  "actions": [
    { "kind": "tapElement", "selector": { "AXUniqueId": "emailField" } },
    { "kind": "type", "text": "test@example.com", "pressEnter": true },
    { "kind": "tapElement", "selector": { "AXLabel": "Sign in" } }
  ]
}
```

Leave out `instanceId` on the per-instance server, which is already bound to one simulator. A `type` action writes into the focused field, so tap the field first. Selectors match on `AXUniqueId`, `AXLabel`, `AXLabelContains`, `type`, `title`, `titleContains`, and `AXValue`, and every field you supply must match.

When the agent has a shell, the CLI runs the same actions one command at a time:

```bash
lim ios tap-element --ax-unique-id emailField
lim ios type "test@example.com" --enter
lim ios tap-element --ax-label "Sign in"
lim ios open-url "myapp://orders/42"
```

## Read what happened

Three signals tell the agent whether the app works, not just whether the taps landed.

**The screen.** Call `ios-screenshot-and-element-tree` after every batch and compare the tree with what the flow should have produced.

**The app's logs.** UI that looks right can sit on top of a failed request. `ios-logs` returns the last log lines for a bundle ID, 200 by default. From a shell:

```bash
lim ios app-log com.example.MyApp --tail 200
```

**A link for a person.** Every simulator has a Signed Stream URL that opens the live device in any browser, with no sign-in. Anyone with the link can control the simulator, so share it only with people who should have access. For a review after the fact, record the run:

```bash
lim ios record start
lim ios record stop -o ./run.mp4
```

## Android

The Android tools follow the same pattern: `create-android-emulator` on the remote server, then `android-screenshot-and-element-tree`, `android-use`, and `android-open-url`. From the CLI, `lim android create` waits for the emulator and starts an ADB tunnel in the background, so existing tooling sees it as a connected device:

```bash
lim android create
adb devices
```

From there, `adb install` and the rest of your Android tooling work as usual. [Run an Android emulator](/android/run-emulator) covers the CLI and SDK in full.

## Troubleshooting

**Every MCP call fails authentication.** The two servers take different credentials. The per-instance server takes the instance's `status.token`, not your organization API key. The remote server takes OAuth or an organization API key.

**The MCP URL is missing.** `status.mcpUrl` is set when the instance is assigned and works once it is `ready`. Create with `wait: true`, or poll `get-instance-status` until the state is `ready`.

**The simulator disappeared mid-session.** Check the inactivity and hard timeouts. An open but idle tunnel does not count as activity.

**`--reuse-if-exists` keeps creating new instances.** Reuse needs at least one label and matches the label set exactly, in the region that handles the create. A different label value, or a create that lands in another region, starts a new instance.

**The element tree fills the agent's context.** Filter it before it reaches the model. This prints only buttons:

```bash
lim ios element-tree --json | jq -c '.. | objects | select(.type? == "Button")'
```

**A selector matches nothing.** iOS creates list rows only when they scroll into view, so a row below the fold is often absent from the tree. In `ios-use`, put `scroll` actions before the `tapElement` in the same batch. On the CLI, add `--scroll-search`.

**Two agents are driving the same device.** Everyone using the same simulator controls the same screen. Give each agent, pull request, or session its own instance with labels.

**The stream link stopped working.** A Signed Stream URL works only while its instance runs. If a timeout terminated the instance, create a new one and share its new URL.

**Actions land but the app does not respond.** Bring the app to the front with `ios-app`, then check `ios-logs` for a crash. To keep one app in front for a whole session, create the simulator with `--force-bundle-id`; after the app first reaches the foreground, Limrun brings it back whenever it is closed or backgrounded.
